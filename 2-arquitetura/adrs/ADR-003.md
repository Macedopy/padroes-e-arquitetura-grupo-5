# ADR-003: Integração com Legado de Leitos via Arquitetura Hexagonal, ACL e Lock Distribuído

* **Status:** Aprovado
* **Data:** 2026-09-20
* **Contexto e Problema:** O sistema de regulação de leitos legado não pode ser desligado e opera em paralelo com a nova solução. Existe risco crítico de *overbooking* (dupla alocação do mesmo leito por sistemas diferentes).

* **Decisão:** Isolar a integração com o legado utilizando **Arquitetura Hexagonal (Ports & Adapters)** com uma **Camada Anti-Corrupção (ACL)**. Para garantir a consistência estrita durante a transição, será adotado o travamento temporário de leitos utilizando **Lock Distribuído via Redis (Redlock)** antes da confirmação no sistema legado. Esta é a decisão de maior risco do projeto — a validação do mecanismo de lock e outbox é o objeto do spike da Entrega 3.

* **Alternativas Consideradas:**
  * **Reescrita completa do legado antes de iniciar a integração.** Descartada: o legado não pode ser desligado e o prazo do projeto não comporta substituição total antes de entrar em operação; a restrição do Envelope C exige convivência com o legado, não sua eliminação imediata.
  * **Two-Phase Commit (2PC) distribuído entre o novo sistema e o legado.** Descartada: o legado expõe apenas uma API antiga e pouco documentada, sem suporte a protocolo de transação distribuída (XA), tornando 2PC tecnicamente inviável.
  * **Reserva otimista com resolução de conflito posterior (last-write-wins ou reconciliação manual).** Descartada: o custo de um conflito é a dupla alocação real de um leito hospitalar, um risco inaceitável para se resolver depois do fato.
  * **Lock via banco relacional compartilhado (`SELECT FOR UPDATE`) direto na base do legado.** Descartada: o legado não expõe acesso direto ao banco de dados, apenas API, então não há tabela compartilhada para travar.

* **Consequências:**
  * **Positivas:** Prevenção de dupla reserva de leito, desacoplamento total do modelo de dados legado em relação ao novo domínio, facilidade para desligar o legado no futuro substituindo apenas o adaptador.
  * **Negativas:** Dependência do Redis como serviço de coordenação de locks. Observação de risco residual: o Redlock oferece garantias fortes apenas com múltiplas instâncias Redis independentes; rodando sobre uma única instância, a proteção contra *split-brain* é mais fraca do que o algoritmo pressupõe, o que deve ser considerado no spike da Entrega 3.
